# Pitwall website

Static marketing site for Pitwall: a one-screen landing page built around a demo,
`/download/`, `/docs/how-it-works/`, `/docs/quick-start/`, `/changelog/`, `/roadmap/` and a 404.

`/changelog/` and `/roadmap/` are rendered at build time from the repository's
`CHANGELOG.md` and `ROADMAP.md`: each page has a `<!-- markdown:<name> -->` marker
that the `pitwall-markdown-pages` plugin in `vite.config.js` replaces with the output
of `scripts/pages.mjs` (a small Markdown converter in `scripts/markdown.mjs`, for the
subset those files use). Edit the Markdown files, not the pages.

Plain HTML pages and one CSS file, bundled by Vite. No framework, no analytics, no
external CDNs. The one outside request is the download page asking GitHub's API for
the latest release. Fonts (Inter, JetBrains Mono, Barlow Condensed) are self-hosted
from `@fontsource` packages.

## Run

```sh
cd website
pnpm install --ignore-workspace
pnpm dev                       # http://localhost:4321 (pages only; no live demo in dev)
pnpm build                     # live demo + pages → website/dist, served from /
pnpm build --base /pitwall/    # same, for a sub-path (GitHub Pages project site)
pnpm build --skip-demo         # pages only (the demo frame says it isn't in the build)
pnpm preview                   # serve dist locally
```

`pnpm build` runs `scripts/build.mjs`: first `scripts/build-demo.mjs` builds the app's
browser mock (repo root, needs `pnpm install` there) into `public/demo/` with the base
`<base>demo/`, then `vite build` builds the pages with the same base. Pages are written
with root-absolute links (`/docs/…`, `/download/`); the `pitwall-site-links` plugin in
`vite.config.js` prefixes the base on the ones Vite doesn't handle itself (anchors,
`data-*`), so the same source works at `/` and under `/<repo>/`. In JS, use
`import.meta.env.BASE_URL`.

The GitHub owner and repository name live only in `site.config.js`; pages use
`%REPO_URL%`, `%RELEASES_URL%`, `%RELEASE_API_URL%` and `%PAGES_URL%`. Deployment is
`.github/workflows/pages.yml` (base from the repository name).

Search and link previews come from the `pitwall-seo` plugin in `vite.config.js`: each
page only writes its `<title>` and `<meta name="description">`; the plugin adds the
canonical URL, Open Graph / Twitter card tags (image `public/og.png`), theme-color and,
on the home page, JSON-LD. URLs are absolute, from `PAGES_URL`. The 404 page gets
`noindex`. The build also writes `sitemap.xml` and `robots.txt` into `dist`. The preview
image is rendered by `node scripts/og-image.mjs` (headless Chrome, demo content only).

## Docs pipeline

The reference pages (`/docs/cli/`, `/docs/settings/`, `/docs/agents/`, `/docs/detection/`)
and the Extensions pages (`/docs/extensions/…`, marked Preview) are rendered from
Markdown in `docs/reference/` and `docs/reference/extensions/`, so they read well on
GitHub too. Relative links between those files become site links; any other repository
path links to GitHub.

**Add an Extensions page:** write `docs/reference/extensions/<page>.md` (a `# ` title,
an intro, `## ` sections), add a row to `EXTENSION_PAGES` in `scripts/pages.mjs` (it
feeds the sidebar, the sources, the Vite input and `llms.txt`), and copy
`docs/extensions/quick-start/index.html` to `docs/extensions/<page>/index.html` with
its own `<title>`, description and `<!-- markdown:extensions-<page> -->` marker.

- **Child pages.** A docs page can have child pages: in the sidebar they are a sub-list
  under it (open on the family's own pages, closed elsewhere; on phones a second row of
  pills), and each child page gets breadcrumbs in place of its eyebrow and Previous /
  Next through the family. The Extensions overview's children are the other Extensions
  pages (listed flat in their group). Families are built in `docsNav()` in
  `scripts/pages.mjs`.
- **Split pages.** `SPLIT` in `scripts/pages.mjs` turns a long Markdown file into a
  parent and one child page per `## ` section at build time, so the source stays one
  file. The CLI reference is split: Install, How it works, Exit status, Recipes, Global
  options and Commands stay on `/docs/cli/`, and each command gets `/docs/cli/<command>/`
  with its `### ` headings moved up a level. The child pages' HTML is generated from the
  parent's page (`writeChildPages`, ignored by git). Links to the old anchors
  (`cli.md#agent-new`, `#agent` in the file itself) are rewritten to the child page, and
  the parent page carries a moved-anchors map and a small script that sends an old
  `/docs/cli/#agent-new` on to `/docs/cli/agent/#agent-new`; the link check reads the
  same map. Settings, Agent definitions and Detection rules are short enough to stay
  whole.
- **Examples from source.** A page never holds example code of its own. Inside a fenced
  block, a line `{{#include <path>#<region>}}` (path from the repository root; without
  `#<region>` the whole file) is replaced by that region, which the source marks with
  comment lines `docs:start <region>` … `docs:end` (`scripts/includes.mjs`). A missing
  file or region fails the build.
- **WIT reference.** `scripts/wit-docs.mjs` turns the `.wit` files in
  `crates/pitwall-tile-host/wit/` and their `///` doc comments into Markdown, which goes
  where `docs/reference/extensions/wit.md` has `<!-- wit-reference -->`. With no WIT
  there it adds nothing. `pnpm wit-docs` prints it, `--wit <dir>` reads another folder,
  `--strict` fails on items without a doc comment; `PITWALL_WIT_DIR=<dir> pnpm build`
  previews another folder on the site.
- **`/sdk/llms.txt`.** The Extensions pages in sidebar order as one plain Markdown file
  for coding agents, with includes and the WIT reference filled in and links absolute
  (`llmsTxt` in `scripts/pages.mjs`; served in dev too).
- **`/sdk/pitwall-extension-authoring/SKILL.md`.** The SDK's authoring skill
  (`sdk/pitwall-extension/skills/`, the file `pitwall extension new` writes into
  projects), copied as is for the For coding agents page to link to (`SKILL` in
  `scripts/pages.mjs`; served in dev too).
- **Examples in the templates.** Most examples are regions of the tile templates in
  `crates/pitwall-cli/templates/tile/`, which CI builds and tests. `pitwall extension
  new` drops the `docs:start` / `docs:end` lines when it writes a project, so they
  never reach an author's code.
- **Link check.** After `vite build`, `scripts/check-links.mjs` checks every `href` and
  `src` in `dist`: each must name a built file under the base, and each `#anchor` an id
  on that page; unfilled `%PLACEHOLDER%`s fail too. External links are skipped unless
  you pass `--external-links` to `pnpm build` (or `--external` to `pnpm check-links`).
  `pnpm build --skip-link-check` skips it.
- **Tests.** `pnpm test` (`node --test`) covers includes, the WIT parser, the link check
  and the Extensions pages. CI runs it and the build in the "Web demo (build + test) and
  website" job.

## Features carousel

Below the demo, a row of four cards ("One layout": terminals, files, source control,
web; `.layout-ov`) shows the demo's view for each (`data-demo-view` on the card; without
JavaScript they are links to `#demo`). Then one section shows, as slides of equal size,
what the demo can't: "Agents show you files" (an agent opening files for you),
"Answer from anywhere" and "Accounts per project". Keep it to what
the demo doesn't show; a feature the demo shows gets a demo tab instead. Each slide has a heading,
an animated mock-up (decorative, `aria-hidden`, CSS keyframes only) and one link to the
docs. No paragraphs or fact lists: the animation has to say it, and the details belong in
`/docs/how-it-works/`. The track is a CSS scroll-snap row (swipe, trackpad, ←/→, the arrows or the tabs);
it is a grid and each slide a subgrid of its three rows, so all slides are as tall as the
tallest and their stages line up. `src/main.js` (`setupCarousel`) marks the shown tab and
makes the other slides `inert`; they show their still (`.feat-idle` turns their animation
off), so a slide's loop starts from the beginning when it is shown. There is no
auto-advance. A link to a slide's id or to anything in it (`#files`, `#away`,
`#accounts`) shows that slide. Without JavaScript the tabs are plain links and the track
scrolls sideways.

**To add a feature:**

1. In `index.html`, add a tab to `.feat-tabs`:
   `<a role="tab" id="ft-<id>" href="#<id>" aria-controls="<id>" aria-selected="false">Name</a>`.
2. Add a slide to `.feat-track`, in the same order:
   `<article class="feat-slide" id="<id>" role="tabpanel" aria-labelledby="ft-<id>" aria-roledescription="slide">`
   holding, in this order, `<div class="away-copy">` (an `h2` only), the stage, and
   `<p class="feat-more">` with one link to the feature's docs section.
3. The stage: `<div class="<x>-stage glass" data-<x> aria-hidden="true"><div class="<x>-scene">…`,
   drawn at 960×600 (and 500×690 on phones, so every stage has the same shape), with its
   keyframes in `site.css` under its own prefix. In `src/main.js`, add `[data-<x>]`, its
   scene and its phone width to the stage-fitting list and to the `motionIO` selector; in
   `site.css`, add its scene to the `.feat-idle` rule and to the `.motion-paused` pauses.
   Its base styles (no animation) are the still shown with reduced motion.

**The "New in" pill.** The newest feature's tab (a demo tab or a slide's; now the
demo's Web tab) carries `<span class="feat-new">%NEW_LABEL%</span>`; the text comes
from `NEW_LABEL` in `site.config.js` (filled in at build time like `%REPO_URL%`). Set it
to the release that ships that feature, and move the span to the next new feature's tab
when there is one.

## Downloads

`/download/` has a card per OS; the visitor's OS (`navigator.userAgentData`, else the
user agent) goes first. Every button links to `%RELEASES_URL%` in the HTML, so the
page works without JavaScript. `src/main.js` then reads `%RELEASE_API_URL%` (GitHub's
latest release, cached for 10 minutes in `sessionStorage`) and points each button at
the asset whose name ends with its `data-asset` suffix (`_universal.dmg`,
`_x64-setup.exe`, `_amd64.AppImage`, …), with the version, date and file sizes. When
the API fails, is rate-limited or there's no release, the buttons stay on the
Releases page and a note says so. Asset names come from `.github/workflows/release.yml`.

## Demo

The landing page's demo is the web demo of the UI, live: the React build of the UI in its browser mock mode, built by
`scripts/build-demo.mjs` into `public/demo/` and loaded in an iframe
(`<base>demo/?onboarded&shots=1&demo=1&theme=dark|light`). There is no video.

- **Loading.** `src/main.js` adds the iframe after the page's `load` event, once the
  frame is within 300 px of the viewport, so the hero never waits on the app. Until
  the app reports ready, a CSS skeleton of the app's layout fills the frame: no image,
  in the page's theme, the same size as the app, so nothing shifts when it appears.
  If `public/demo/` isn't in the build, the frame says so.
- **Size.** The app renders at 1120×700 (it shows its full sidebar from 1100 px) and
  is scaled to the frame. Below 600 px the frame is 4:5 and shows the app's left half
  (sidebar and first tile) at twice the scale, so text stays legible on phones; a tab
  with `data-phone="right"` (Files, Web, Next up) shows the right half instead, where its
  tile or the Next up popover is.
- **Tabs.** It is the page's one main demo, strongest views first: Needs you / Files /
  Web / Review / Wall / Next up post `{ type: "pitwall-demo", view }` to the app;
  `src/lib/demoBridge.ts` (inert outside the browser mock and without `?demo=1`) clicks
  the app's own controls and replies `{ type: "pitwall-demo-ready" }` once agents are on
  screen. Files opens api-fix's `src/orders/handler.ts` from the palette's Browse files:
  a files tile beside its terminal, with git status. Web clicks Preview on the docs
  agent, whose terminal printed a local address: a web tile beside it with a made-up
  page drawn in HTML (`src/components/WebTile.tsx`, `src/mockWeb.ts`; no iframe, no
  network). On phones the tab row scrolls and drops the shortcuts.
- **Theme.** The page's theme goes in as `?theme=` and again as
  `{ type: "pitwall-demo", theme }` whenever the toggle (or the OS setting) changes.
- **State.** Each load clears the mock's `pitwall.*` localStorage keys, so every
  visitor starts from the same demo. The mock data only uses placeholder paths and
  names (`/Users/dev`, `dev@mac`).

**The README animation** (`docs/media/demo.webp`) is a separate recording of the
mock: `pnpm demo:serve` (port 5199) and `scripts/record-demo.mjs` capture frames over
CDP at 1120×700; encode at 10 fps, 1120 px wide, `img2webp -lossy -q 55`.

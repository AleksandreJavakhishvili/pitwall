How it works

Pitwall hosts terminal coding agents. It isn't an agent itself: it never rewrites prompts or decides what an agent does. This page covers the parts the home page only names.

Flags

Each agent has one flag, shown in the sidebar, its pane header and its Wall tile. Within a project, agents sort needs you → done → working → idle, then the rest.

Example agents and their flags
PosAgentFlagDetail
1tests▲Needs youBash: pnpm test --run src/cart
2docs⚑Done finished a turn you haven't looked at
3api-fix◐Workingoutput is flowing
4refactor●Idlewaiting for a prompt
5scratch■Stoppednot running; Restart resumes it
  • Needs you: a permission prompt or a question. Amber row, a bar along the bottom of the window, counted on the Dock badge. ⌘J jumps to the next one.
  • Done: finished a turn you haven't looked at. Looking turns it idle.
  • Working: output is flowing, or the agent's hook says it's busy.
  • Idle: waiting for a prompt. Unknown (?) means there's no signal yet.
  • Exited / stopped: the process ended, or it was loaded after a restart and isn't running.

When the window isn't focused, needs you and done also post a native notification.

How it knows

  1. Hooks, when the agent has sent one this run. Claude Code gets its hooks per launch through --settings; ~/.claude/settings.json is never edited. Codex hooks are opt-in, and ~/.codex/hooks.json is backed up first.
  2. The screen. A headless copy of each terminal is matched against per-agent TOML rules, adapted from Herdr's detection manifests (Apache-2.0). Always on.
  3. Activity. For any other CLI: output in the last ~1.2 s means working, otherwise unknown.

Hooks are never required.

Wall

⌘E shows every agent's terminal, grouped by project, blocked first. Tiles show the bottom rows of each terminal, where prompts wait. The Wall is view-only: it never resizes a terminal and never types. Click a tile to take over that agent; Esc comes back. A window left in Wall mode stays that way across restarts.

Answering from another app

While you're in another app and an agent's screen asks you something, a small pill floats over your desktop, on every Space and over full-screen apps. It never shows while Pitwall is in front, and it goes away when nothing waits.

  • The pill: The agent that has waited longest: its logo, its name (and its project when two share a name), one plain line of what it wants, such as Run: pnpm test, Edit src/cart/total.ts or the question it asks, and +2 when others wait. For a plain yes or no it has Accept and Reject; for anything more, Open brings Pitwall forward on the agent. A command too long to name in one line shows Show instead, so you see all of it before you answer. The pill never takes the keyboard.
  • The card: Click the pill for one card at a time, oldest first, with 1 of 3 and arrows. It names what the prompt asks, in lines of the prompt itself, over the rows of the agent's terminal that ask, drawn live; Show all shows the whole prompt. When Pitwall can't read the action off the prompt reliably, you get the terminal rows alone. ⏎ accepts, esc rejects, ←/→ go between prompts; other keys go to the agent's terminal as in its pane. Accept all appears only when every prompt that waits is a plain yes or no.
  • Nothing blind: Before typing an answer, Pitwall reads the agent's screen again and types only if the same prompt is still there. After an answer the control says Sent to api-fix for about a second and moves to the next prompt; if the prompt changed, it says The prompt changed: nothing was sent and shows the new one. An agent on another machine is shown, never answered from here.
  • Where it sits: Drag it anywhere; it stays there, also after a restart. Resize the open card by any edge or corner, and double-click an edge for the default size. It slides in once when it appears, not with Reduce motion. Off with general.floatingPrompts. Your extensions' inbox questions show up here too, after your agents'. Liquid Glass on macOS 26 with the Glass look.
  • Tested: Accept and Reject keys were checked against Claude Code and Codex; the other agents' are written from their prompts and not yet checked against the real CLIs. Run on macOS; the Linux and Windows builds have the control, but it hasn't been run there.

Review

⌘R lists changes by agent, then file, in a side-by-side or inline diff. Pick All changes or one task: a single prompt, from send until the agent is done.

  • Per-task snapshots are written through a temporary index (GIT_INDEX_FILE), so your real index and working tree are never touched. Untracked files are included.
  • Click a line to comment. Send comments shows the composed prompt for editing first, then sends it to the agent exactly as written.
  • Commit & merge runs git merge --no-ff of the worktree's branch, only when you click. It refuses if your main checkout is dirty; on a conflict it runs git merge --abort and offers the agent an editable "rebase and resolve" prompt.
  • The diff editor is bundled, so Review works offline.

Files agents show you

Ask an agent to open a file, a folder, a worktree or an image ("open that file for me", "show me worktree fix-retry") and it opens in Pitwall's file viewer, in a files tile: a slot of its own in the layout of the window that shows the agent, right of its terminal unless you ask for left, above, below, another agent's terminal, or a terminal's place. A terminal it replaces keeps running and is back from the sidebar. Ask for a window and it gets a window of its own. Drag the files by their bar anywhere in a window's layout or out into a window and back; Move… and Dock… do the same without dragging. Pitwall doesn't come forward over the app you're in, and the terminal keeps the keyboard. Tiles come back after a restart with what they had open.

  • How agents ask. Pitwall's own MCP server (pitwall-cli mcp, tools show_files and show_folder) is added to each launch of Claude Code, Codex, Copilot CLI, Qwen Code, Amp and opencode through the tool's own flags or environment; your config files aren't edited. Gemini CLI and Cursor Agent only read their own MCP files, so Settings → Agents offers to add Pitwall's entry there (a backup is kept; Remove takes it out). Aider gets a short rule to run pitwall-cli open, and pitwall open does the same from any shell. Showing files was tried by hand with Claude Code; the other agents' routes are built and tested in code but not yet run against each real CLI. Details in Showing files; off with agents.showFiles.
  • Where it works now. The files come from the folder the agent works in now: a worktree Claude Code entered mid-session, or a folder a shell cd-ed to. The tree has that worktree's branch and git status, and Show diff opens Review on it.
  • What it shows. Text and code with highlighting and Find, Markdown as code or preview. Images (PNG, JPEG, GIF, WebP, SVG) fitted, at 100 % or zoomed on a checkerboard; an SVG switches between Picture and Source (⌘⇧V). Other binary files offer Open in default app. The tree hides and shows with ⌘⇧E and its edge drags it wider, as does Review's list of changes.
  • PDFs: macOS only for now. Pages one under the other, Fit, 100 % or zoomed, the page you're on, and Find (⌘F), drawn by the system's PDF engine. On Windows and Linux a PDF says it can't be shown in Pitwall yet and offers Open in default app.
  • Quick fixes. Edit a text file where it's shown and save with ⌘S: undo, Tab in the file's own indentation, Replace and Replace All; line endings and the final newline stay as they were. A dot marks unsaved tabs, and closing asks first. When the agent changes the file meanwhile, it is read again quietly if you have nothing unsaved; otherwise Keep mine, Take theirs or Show difference. Only files of agents on this computer; other machines' files, images and binary or large files stay read-only. Agents still can't write through Pitwall. Off with agents.editFiles.

Web pages

⌘L (Ctrl+Shift+L on Windows and Linux), or Open web page… in the command palette, opens a page in a web tile next to your terminals, in the system's own web view: type an address (example.com, localhost:3000; there's no search), go back and forward, reload, or open it in your browser. Web tiles move, resize and come back after a restart like files tiles; Open in a window of its own (or Move…) gives a page its own window, and Dock… brings it back as the same page.

  • Preview. When an agent's terminal prints a local dev server's address, its header shows Preview :<port>. It opens the server in a web tile right of the terminal that follows it: a new address is loaded, the same one printed again reloads, and a stopped server says so.
  • Pages agents open. Ask an agent to open a page, a local dev server or an empty browser ("open the docs on the left") and it opens in a web tile beside its terminal, through Pitwall's MCP tool show_web or pitwall open --web, which agents get the same way as the files tools. It only shows you the page: the agent gets nothing back from it and can't click, type or read anything in it, and the keyboard stays where it was. Details in Showing web pages; off with agents.showWeb, or every web page with general.webPages.
  • Settings agents open. Ask an agent where a setting is and it opens Pitwall's Settings at that page in the Settings tile next to its terminal (or switches the one you have), through Pitwall's MCP tool show_settings or pitwall open --settings. It only shows you Settings: the agent gets nothing back from it and can't change anything there, and the keyboard stays where it was. Details in Showing Settings; off with agents.showSettings.
  • Browser accounts. A browser account is an account of its own kind in Settings → Accounts: a name ("Work", "Personal") with its own sign-ins, cookies and site data. A project picks one in its Accounts… dialog. Pages its agents open use it, and so does a page you open with ⌘L while one of its agents has the focus; anything else is in Default. The agent can't choose one. Each page's bar shows its account, and its menu moves the page to another (it loads again there). A browser account with pages open can't be removed; removing one deletes its sign-ins and site data from this computer, and its projects go back to Default. A profile (Settings → Profiles) bundles a project's picks under one name, such as Work: its tool accounts, git identity, browser account and extension connections. Browser accounts other than Default need macOS 14 or later. Kept apart as checked by hand on macOS 26; on Windows and Linux they are built and tested in code only. Details in Browser accounts.
  • Limits. WebKit on macOS, WebView2 on Windows, WebKitGTK on Linux (X11): one page per tile, no tabs, search or extensions. Logins stay in Pitwall's browser accounts, not your browser's. Camera and microphone are denied for now, so calls don't work; macOS declines downloads and offers the browser instead. Web tiles were run by hand on macOS only.

Terminals that outlive the app

Each agent's terminal belongs to its own pitwall-hold process, not to the app. ⌘Q closes the UI; dev servers and half-finished turns carry on, and the next launch re-attaches with the scrollback replayed. Only Stop, Restart, Remove or Quit and Stop Agents end a terminal. After a reboot, agents come back stopped, and Restart resumes the conversation for CLIs that support it.

Pitwall.app   UI, quit any time
   │ attach · write · resize · replay
   │ ~/.pitwall/run/hold/<agent>.sock
   ▼
pitwall-hold  one per agent, setsid, owns the PTY
   ▼
claude --session-id 7f3c…   still running

Stop / Remove → SIGHUP, SIGKILL after 1.5 s

Spaces and windows

Spaces are tabs of tiled terminals. Presets: 1, 2, 1 big + 2, 2×2 and 3×2, plus 3×3, 4×3 and 4×4 when the window can fit them, and Auto grid. Drag an agent onto a pane edge to split, onto the centre to swap. An agent sits in at most one pane; extras fold into a chip strip. ⌘⇧N moves a space into its own window, and layouts, windows and bounds come back on launch. Moving a terminal never restarts it. Settings can be a tile too: "Open as a tile" in its dialog (or "Open Settings as a tile" in the command palette) puts every page at the tile's full size, and it moves, maximises and opens in a window of its own like the others.

Accounts

Claude Code, Codex, Gemini CLI and Copilot CLI can run on more than one login, say a work and a personal subscription. An account is one login of one tool: a name and the folder the tool keeps its login in (CLAUDE_CONFIG_DIR, CODEX_HOME, GEMINI_CLI_HOME, COPILOT_HOME); Default is your own. A work Claude Code and a work Codex are two accounts, each picked on its own. Cursor Agent, opencode, Amp, Aider and Qwen Code have no setting that moves their login, so they run on one.

  • Add one in Settings → Accounts, or from a project's right-click menu → Accounts…. Log in opens the agent on that account so it asks for its login; Settings shows who each account is logged in as.
  • Per project: right-click a project → Accounts… sets the account its new agents use for each tool, a git identity for its commits and pushes, and a browser account for its web pages, and offers to move the agents already there. A profile (Settings → Profiles) bundles these picks under one name, such as Work, and a project then picks the profile.
  • By dragging: with the sidebar grouped by account (Settings → General), drag a project or an agent onto another account.
  • Per agent: New agent has an account choice, and an agent's right-click menu → Run on account moves it. Moved agents restart on the new login at once; Claude Code and Codex resume their conversation, the other tools start a new one. An account that isn't logged in yet is refused instead of leaving the agent stuck.
  • Usage: Settings → Accounts shows Codex's plan limits and Claude Code's tokens, read from the tools' own files.
  • Stays here: accounts are login folders on this computer, listed in ~/.pitwall/accounts.json. There is no Pitwall account, and nothing is sent anywhere. Agents on this computer only.

Any agent kind whose definition names a login folder variable (account_env) gets the same support.

Rules

Keep rules in ~/.pitwall/rules/, group them into named sets, and assign a set per project with optional extras per agent. Pitwall calls the rulesync CLI to write CLAUDE.md, AGENTS.md and the rest; it doesn't reimplement it.

  • Import from a project's .rulesync/, an existing CLAUDE.md or AGENTS.md, or a git repo.
  • Generated paths go into the worktree's .git/info/exclude, so they never show up in Review or a commit.
  • Agents in your main checkout only get rules when you tick the box.
  • Uses rulesync on PATH, or npx -y rulesync only if you enable it in Settings.

agw machines

If you use agw to run agents on VMs, its sessions show up in Pitwall next to your local agents, grouped by machine.

  • Works today: add an existing session and get its live terminal, its flag (from screen detection), stop and start. Diffs and Review run git on the VM through agw. New agent → Runs on creates a session on a VM with agw's own workspaces, users and templates.
  • Not yet: hooks and rules on VMs (status comes from the screen only), merging from Review, and deleting a session on the VM. Removing an agw agent from Pitwall only detaches it; the session keeps running there.

CLI and approvals

Settings → Install command-line tool links pitwall into ~/.local/bin or /usr/local/bin. It talks to the running app over a local socket and prints JSON (--human for text).

pitwall agent list
pitwall agent new --kind claude --project ~/code/api --name api [--account work] [--prompt "run the tests"]
pitwall session list --provider agw
pitwall session add agw <vm> <session> --start
pitwall settings list
pitwall settings set appearance.theme dark
pitwall space move "API" --to-window new
pitwall wait api --for done --fresh

It does what the UI does: agents (new, optionally with a first prompt; stop, restart, remove, rename, status), spaces and windows, projects, rules, read-only review and settings, plus wait so agents can coordinate. Stopping, restarting or removing an agent asks for your approval when anyone but you asks. Settings are also plain JSON in ~/.pitwall/ui.json (with a JSON Schema for editors): edits apply live, and a value that isn't allowed is reported while the last good one stays. Settings that change something outside Pitwall, like installing Codex hooks, ask for your approval when an agent changes them. Anything that changes another machine (starting or creating a session on a VM) opens an approval dialog in Pitwall and the command waits for your answer. A denial exits with status 3. The app works out who's asking from the calling process, so an agent can't approve its own request. Every command and option is in the CLI reference, every setting in the settings reference.

The optional Race Engineer (the headset in the top bar, or ⌘K) is an agent that already knows all this: it runs on the agent you pick in Settings → Agents, in its own folder in Pitwall's data folder, with Pitwall's instructions and this CLI reference written there as AGENTS.md, CLAUDE.md and GEMINI.md, and pitwall on its PATH. Your ~/.claude and ~/.codex are not touched.

First launch

A read-only scan: agent CLIs on your PATH, recent projects from Claude and Codex transcripts, VS Code and Cursor history and one level deep in ~/projects ~/code ~/Developer ~/src ~/dev ~/work, and conversations you can continue. Desktop, Documents and Downloads aren't enumerated; use Add folder…. Nothing changes until you tick a box. Details are in the quick start.

Performance

Pitwall is a native Rust app. The UI is drawn on the GPU with GPUI, Zed's UI framework, in the same process as the engine: there is no web view, and terminal output never crosses a bridge to be drawn. Terminals are parsed with alacritty_terminal, Wall tiles are drawn from those same screens, and git for local agents refreshes when files change instead of on a timer.

Glass uses the system's own material: Liquid Glass on macOS 26, vibrancy on older macOS, Mica on Windows 11. Terminals stay opaque. Measurements, against the 0.1 releases that ran in a web view, are in the README.
